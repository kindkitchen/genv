# Pivot: source-agnostic engine, GitHub mapping moves to an adapter

Drop the action.yml coupling from the engine core. The engine must know nothing
about GitHub, "vars", "secrets", or include/exclude/content_from patterns. Those
are caller concerns and move to a thin adapter owned by slug action-js-parity.

Reframed as three technical primitives:

1. Multiple ordered sources — public vs private is just labeling the caller
   attaches; the engine takes N sources and nothing more, no special-casing.
2. Two value kinds — a `key=value` whose value is a literal, and a `key=value`
   whose value is itself env-file content (key=value pairs) to be parsed and
   inlined. This distinction is structural (fragment kind), not regex-on-key-name
   as the old content_from_* patterns did it.
3. Merge N sources into one, preserving merge order, last-win on conflict.

Structure:
- core (pure TS): ordered last-win merge over sources + nested-content expansion.
  No I/O, no GitHub.
- utils: `parse` (env-file text -> js object) and `stringify` (js object ->
  env-file text). Load-bearing, not cosmetic: `parse` expands a content fragment
  into pairs; `stringify` is the final render.
- tests: spec/unit for core + utils; e2e for the full pipeline + CLI.

Working assumptions (challenge, don't replace):
- merge collapses conflicts into a final resolved object (true last-win),
  replacing the old bash-fidelity behavior of emitting duplicate lines. The
  duplicate-line output was an action.yml artifact, not a requirement.
- "value is content" is expressed by fragment shape (content vs kv), not a
  key-name pattern.

Public-API impact: the current `genv(inputs)` with GitHub-named inputs
(vars_obj, secrets_obj, *_include/_exclude, content_from_*) is superseded; the
GitHub shape survives as the adapter consumed by action-js-parity, and bash-byte
parity is no longer an engine goal. Packaging from [[002.decision]] stays (Deno +
JSR, `import.meta.main` CLI); semantics from [[001.draft]] are reframed by this.
